# Лабораторная работа — шаблон MVVM

**Тема:** AMFIBIA Studio — панель управления маркетплейсом брендовой одежды
[Fashion_site](https://github.com/JLeizy/Fashion_site). Если приложение из ЛР №28 (шаблон MVP) — это магазин
для покупателя, то здесь рабочее место сотрудников магазина. Те же 15 модных домов и 714 вещей, а ещё
заказы, склад, отзывы, промокоды, курсы валют, пользователи и полные статьи об истории брендов с сайта.
Приложение написано по шаблону **Model — View — ViewModel** (WPF, C#, .NET 10).

## Как открыть и запустить

1. Открыть **Visual Studio 2026** → «Открыть проект или решение» → `Lab_MVVM.sln`.
   Нужна рабочая нагрузка «Разработка классических приложений .NET» (.NET 10).
2. Нажать **F5**.
3. Нажать кнопку демо-аккаунта под формой входа (пароль у всех **`Amfibia2026`**) и «Войти в панель».

Каждая роль видит свои разделы (как проверки ролей на сервере сайта):

| Аккаунт | Роль | Разделы |
|---|---|---|
| `owner@amfibia.by` | Создатель магазина | все 11 разделов |
| `moderator@amfibia.by` | Модератор | дашборд, товары, отзывы, пользователи, энциклопедия, журнал, настройки |
| `support@amfibia.by` | Поддержка | дашборд, заказы, отзывы, пользователи, энциклопедия, настройки |
| `warehouse@amfibia.by` | Кладовщик | дашборд, заказы, склад, энциклопедия, настройки |
| `courier@amfibia.by` | Курьер | заказы (только курьерская доставка), энциклопедия, настройки |
| `official@amfibia.by` | Продавец | товары, склад, энциклопедия, настройки |

Покупатель (`buyer@amfibia.by`) в панель не попадёт: для него приложение из ЛР №28.

Все изменения сохраняются между запусками в `%AppData%\AMFIBIA\Lab_MVVM\studio.json`.
Вернуть демо-данные можно в разделе «Настройки» (владелец) или удалив эту папку.

## Как устроен MVVM

```
AmfibiaStudio/
├── Models/               МОДЕЛЬ — данные сайта и состояние магазина (товары, заказы, склад…)
│   ├── Product.cs, Brand.cs, Order.cs, User.cs, Reference.cs
│   └── StudioData.cs       загрузка Data/amfibia.json и статей Data/amfibia-history.json
├── Services/             МОДЕЛЬ — сервисы за интерфейсами
│   ├── StudioContext.cs    общий контекст: данные, роли и права, журнал, уведомления
│   ├── StudioStore.cs      сохранение в studio.json (IStudioStore)
│   ├── Services.cs         IDialogService, IThemeService, IRatesProvider (НБРБ), форматирование
│   └── WpfServices.cs      WPF-реализации: окно подтверждения и смена темы
├── ViewModels/           VIEWMODEL — состояние и команды каждой страницы, ничего не знают об окнах
│   ├── Base/               ObservableObject (INotifyPropertyChanged), RelayCommand и AsyncRelayCommand (ICommand),
│   │                       ValidatableObject (INotifyDataErrorInfo), PageViewModel
│   ├── MainViewModel.cs    вход ↔ панель
│   ├── LoginViewModel.cs, ShellViewModel.cs (меню по роли, навигация, счётчики)
│   └── DashboardViewModel.cs … BrandsAuditSettingsViewModels.cs   по одной на страницу
├── Views/                ВИД — только разметка XAML, в коде страниц нет ни одной строки логики
│   ├── LoginView.xaml, ShellView.xaml, ConfirmWindow.xaml
│   └── Pages/              11 страниц: Dashboard, Products, Orders, Warehouse, Reviews, Promos,
│                           Rates, Users, Brands, Audit, Settings
├── Controls/             рисунок товара, кольцевая диаграмма, привязка пароля, цвет заголовка окна
├── Converters/           преобразователи для привязок (видимость, цвета, длина столбцов)
├── Themes/               Colors.Amfibia / Light / Graphite.xaml — цвета тем, Styles.xaml — стили
└── App.xaml(.cs)         DataTemplate «ViewModel → Вид» и сборка: Модель + сервисы + MainViewModel
```

**Чем MVVM отличается от MVP (ЛР №28):**

| | MVP (ЛР №28) | MVVM (эта работа) |
|---|---|---|
| Связь с Видом | Представитель вызывает методы интерфейса Вида (`view.ShowError(...)`) | ViewModel не знает о Виде; Вид привязан к её свойствам `{Binding}` |
| Действия пользователя | Вид поднимает события (`LoginRequested`) | Кнопки привязаны к командам `ICommand` (`Command="{Binding LoginCommand}"`) |
| Обновление экрана | Представитель сам передаёт данные Виду | ViewModel сообщает `PropertyChanged`, WPF обновляет экран сам |
| Проверка ввода | Представитель показывает сообщение | `INotifyDataErrorInfo`: ошибка появляется под полем, кнопка блокируется через `CanExecute` |
| Навигация | Фабрика видов и интерфейс навигатора | `ContentControl` + `DataTemplate`: WPF сам выбирает Вид по типу ViewModel |
| Код Вида | Обработчики событий в .xaml.cs | Только `InitializeComponent()` |

**Правила, которые соблюдаются во всём проекте:**

1. Вид — только XAML. Всё, что он показывает, берётся привязками из ViewModel; все кнопки — команды.
2. ViewModel не использует ни одного класса WPF-окон: окна подтверждения, смена темы и загрузка курсов
   доступны ей только через интерфейсы `IDialogService`, `IThemeService`, `IRatesProvider`.
   Поэтому каждую ViewModel можно проверить без экрана, подставив заглушки.
3. Модель ничего не знает ни о ViewModel, ни о Видах. Об изменениях данных `StudioContext` сообщает
   событием `Changed` — по нему пересчитываются дашборд и счётчики в меню.

### Пример 1. Вход

1. **Вид** `LoginView`: `<TextBox Text="{Binding Email, UpdateSourceTrigger=PropertyChanged}"/>`,
   пароль — через присоединённое свойство `PasswordBoxAssistant.BoundPassword` (у `PasswordBox` нельзя привязать `Password`).
2. **Пользователь** вводит email — привязка сразу записывает его в свойство `LoginViewModel.Email`.
3. **ViewModel** проверяет формат и вызывает `SetError(...)` → событие `ErrorsChanged` → WPF показывает текст ошибки
   под полем (шаблон `FieldError`) и красную рамку.
4. `LoginCommand.RaiseCanExecuteChanged()` → кнопка «Войти» доступна, только когда ошибок нет (`CanExecute`).
5. Нажатие «Войти» выполняет `LoginCommand`: ViewModel ищет сотрудника в **Модели**, проверяет пароль, блокировку и роль.
6. При ошибке меняется свойство `ErrorMessage` — Вид показывает его сам. При успехе событие `LoggedIn` →
   `MainViewModel.CurrentView = new ShellViewModel(...)` → по `DataTemplate` WPF показывает `ShellView`.

### Пример 2. Перевод заказа в следующий статус

1. Кнопка `Content="{Binding AdvanceText}" Command="{Binding AdvanceCommand}"`.
2. `AdvanceCommand.CanExecute` проверяет права роли: например, «Подтверждён» ставит только владелец или поддержка,
   а сборку — склад. Если шаг не ваш, кнопка недоступна, а под ней подсказка `RuleHint`: кто выполняет шаг.
3. `Advance()` применяет правила сайта (`orderService.js`): подтвердить можно только оплаченный заказ (кроме наличных),
   для курьерской доставки нужен назначенный курьер, при статусе «Собран» товар списывается со склада
   (сначала Минск, потом Москва и Алматы), при нехватке — сообщение и статус не меняется.
4. ViewModel обновляет Модель, пишет действие в журнал и сообщает `PropertyChanged` — шкала статусов,
   таблица, счётчик в меню и дашборд обновляются сами.

### Пример 3. Смена темы без перезапуска

Все стили берут цвета через `{DynamicResource Accent}`. `SettingsViewModel.SelectedTheme` вызывает
`IThemeService.Apply("light")`, а `ThemeService` заменяет первый словарь ресурсов приложения
(`Colors.Amfibia.xaml` → `Colors.Light.xaml`) — все окна перекрашиваются сразу.

## Откуда данные

`Data/amfibia.json` выгружен из репозитория сайта по правилам `db/seed.js`: 714 товаров с ценами, 15 брендов
с палитрами, хронологией, директорами и коллекциями, пользователи и роли, способы доставки и оплаты, промокоды,
курсы валют, склады и остатки, статусы заказов. Демо-заказы и отзывы построены по тем же правилам, что в `seed.js`.
`Data/amfibia-history.json` — полные статьи об истории модных домов из `db/content/histories` сайта.

Фотографии товаров в программу не включены (по README сайта они принадлежат правообладателям): как в заглушках
сайта (`scripts/placeholder-art.js`), рисуется силуэт вещи её цветом на фоне в палитре модного дома.
Шрифты — Cormorant Garamond, Inter и UnifrakturMaguntia (лицензия SIL OFL, файлы в `Fonts/`).
